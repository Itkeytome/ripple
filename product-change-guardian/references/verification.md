# Verification Before Product Completion

## 1. 从验收条件选检查，不从工具输出倒推完成

开始修改前确认相关验收与范围外不变条件；有条件时先复现原问题。修改后在最终代码状态运行检查，读取完整相关结果和退出码。

| 变更 | 最少考虑的行为证据 |
|---|---|
| 文案、间距、局部 UI | 目标呈现、指定设计约束、共享入口未被改变 |
| 筛选 | 默认值、选择关系、UI／Store／请求一致、Reset、关闭重开与回显 |
| 表单 | 新增／编辑默认值、条件显示、校验、回显、保存请求与往返结果 |
| 共性规则 | 每个拟同步入口执行同一语义；按范围保留的入口未被误改 |
| 跨端同步 | 业务规则和保存行为一致；各端已有控件、布局与交互保留 |
| 标签替换 | 同语义展示已更新；第三方契约、持久化值、历史迁移等未误改 |

这些是选择检查的提示，不要求每个任务跑全表。合并重复检查，但不能跳过本次真实改变的状态和依赖。

## 2. 筛选／表单状态链

1. 打开页面，确认默认值与请求初值。
2. 选择父选项和子选项，确认从属／互斥关系及显示状态。
3. 检查 Store、请求参数和结果，不能只看标签样式。
4. 执行 Reset，确认所有相关状态同步回到已确定的默认值。
5. 关闭再打开、切换入口或重新加载，检查回显和持久化行为。
6. 涉及保存时检查保存参数、成功／失败处理及重新读取结果。

使用 Mock 或单元测试时说明证据层级；不要将纯逻辑测试当成目标平台运行结果。真实 API 写操作只在有相应授权和安全测试数据时执行。

## 3. 共享依赖与反向扫描

把 Impact Map 中标为“同步”的项逐个核对，把“范围外／不改”作为回归条件。检查最终行为而非只看改了几份文件。

按业务术语、字段、调用关系和映射逻辑反向搜索遗漏。对保留的旧值说明保留理由，不为追求零搜索结果修改迁移、契约或无关语义。

对照批准的 Prototype 和 Design Provenance，检查布局、状态与规则没有在实现中漂移。

## 4. 结果分类

- `PASS`：执行过，实际结果满足相应断言，而且对应最终代码状态。
- `FAIL`：执行过，结果不满足；记录失败位置、原有还是本次引入、影响。
- `NOT_RUN`：没有执行；不能用“预计通过”替代。
- `BLOCKED`：依赖、凭证、设备、网络或运行工具缺失等阻塞；写明具体缺口。
- `N/A`：验收与本次变更确实无关，必须解释原因。

一次命令执行失败后，后续未运行的检查仍是 NOT_RUN，而不是自动 PASS。已有失败与本次回归分别列出；不能假称原有失败已修复，也不应无授权修理无关问题。

## 5. 完成声明

分别说明实现状态与验收状态。所有必需检查都有最终状态的通过证据时，才报告验收完成；有未验证的平台就精确报告哪个平台尚未验收。

例如：“实现已提交到工作区；构建通过，Reset 行为测试通过；小程序真机交互受环境限制未验证。”只有实际发生了相应事实，才能使用这样的表述。

构建与 Lint 仅说明其实际覆盖的检查，不证明交互、产品规则或跨端一致性。子 Agent 的摘要也不替代主 Agent 对差异与证据的复核。

验证后再改代码，就重新运行受影响检查。不要沿用另一版本、另一仓库、另一分支或另一个平台的通过结果。

## 6. 无法完成验证时

执行当前可行的检查，保留已完成工作，交付最短的补验步骤与所需环境。不为让报告显得完整而伪造截图、终端结果、测试数量或工具执行历史。

没有浏览器／小程序开发者工具时，可以检查结构和逻辑并报告限制；不能声称已点击、已预览或已真机验证。
