# Product Change Guardian

守住产品变更的范围、依据、授权和验收。先理解业务语义，再决定改哪里；搜索可以比修改范围大，修改权限不能比用户授权大。

遵循当前环境的指令优先级、权限与安全要求。本 Skill 不授予额外文件、网络或部署权限，也不要求安装其他 Skill。使用用户当前语言沟通。

## 1. 先决定走哪条路径

先读取现有实现，判断已知需求、限制和授权；不要要求用户重复提供对话或项目中已有的信息。

| 可观察条件 | 下一步 | 正式实现权限 |
|---|---|---|
| 用户只要解释、排查结果、评审或方案 | 完成所要求的只读工作 | 不进入实现，不强塞原型流程 |
| 用户明确说“直接改／不用原型，按这些要求做”，且需求与范围清楚 | 完成必要检查，简述变更边界，记录直接授权 | 仅限明确授权范围；其他有效 Gate 仍需满足 |
| 普通产品变更，尚未批准方案，也未明确直接实现 | 提供相称的 Prototype，等待确认 | 未获授权前不修改正式代码 |
| 用户仅反馈原型如何调整 | 更新原型和受影响的方案字段 | 不是实现授权 |
| 用户批准当前明确方案，例如“可以，就按这个开发” | 绑定当前版本与范围，进入实现 | 不重复索取同一批准 |
| 新发现超出授权的页面、业务规则或接口影响 | 说明新增差异，寻找范围内方案；必要时确认新增范围 | 原批准不覆盖新增影响 |

“简单”“赶时间”“已有 patch”不单独构成授权；“直接改”也不消除尚未明确的关键业务选择。按语义识别等价授权，不要求固定口令。

## 2. 建立基线与 Requirement Brief

读取项目适用约定、目标页面、直接依赖及已有设计；记录当前工作区状态与任务起点。保留用户既有改动，不自动 stash、reset、删除或覆盖。

用简短的 Requirement Brief 记录：目标、关键规则、明确包含的范围、不包含的范围、验收条件、未决问题。局部改动可在对话中用数句表达，不强制新建文档。

把“需求复杂度”和“授权范围”分开判断：发现跨端共性规则可以升级分析深度，但不能因此扩大修改范围。已有批准和产物可复用，先核实版本与范围。

缺少关键仓库、参考源或运行能力时，说明具体缺口。可提供标注假设的方案；不可声称已经查过、测试过或遵循了不可见的实现。

## 3. 按业务语义制作 Impact Map

搜索目标实现、共享组件与调用者、同语义入口、状态来源及请求参数；跨端需求再检查相关平台实现。不要只搜文字，也不要扫描无关项目。

对每个相关入口记录：业务含义、文件路径或符号、共享依赖、潜在行为影响、拟处理方式（同步／不改／待定）及理由。先覆盖直接依赖与已发现的同语义入口，再记录未覆盖边界；不要把搜索变成无限审计。

同名不一定同义。用户可见标签、第三方字段、持久化值、历史迁移、数据字典与测试数据分别判断，不能机械 replace-all。

**按行为影响判范围，不按文件数量判范围。** 用户限定“只改首页”时，修改共享组件也必须证明地图等范围外入口保持原行为；必要时使用局部样式或兼容默认值的最小参数化。

对共性问题提出合理同步方案或最小共享抽象；共享抽象须直接服务本次目标、低风险且在授权内。不要借一致性改造整个系统。

## 4. 用 Design Provenance 约束方案

分别记录 UI 来源、业务规则来源、API／数据约束，以及证据状态（已验证／推断／冲突／不可访问）。每个来源指向实际读取的位置；本次新增设计须单独标注。

用户指定精确 UI 参考时，保留其结构、Footer、按钮、间距与操作方式，只改允许的内容；没有精确指定时，优先沿用目标端现有组件和视觉体系。

用户指定后台业务参考时，读取其字段、校验、默认值和状态关系；跨端同步业务语义与保存行为，不照搬桌面布局到手机。

参考实现、当前 API 契约与用户要求冲突时，列出冲突与影响，不凭空选一个作为“项目规则”。没有完全相同的参考时，使用最接近的模式，最小化新增设计。

## 5. 提供相称的 Prototype，通过 Approval Gate

| 变更规模 | 足够的确认材料 |
|---|---|
| 局部视觉调整、不改业务行为 | 项目依据、前后差异与影响范围；精确文字对比或局部示意即可 |
| 筛选、表单、状态关系变化 | 关键交互原型，以及默认值、清空、回显、提交等相关状态 |
| 共性规则、跨端、新交互 | Impact Map、Design Provenance、关键流程原型及必要实现步骤 |

轻量化产物，不省略边界检查。用户明确要求可视原型时，不以一句“将进行优化”代替可审阅产物；环境不支持时说明限制并给可用替代。

原型只使用隔离的静态文件、Mock 数据或已允许的预览工作区。未获正式实现授权前，不修改真实路由、Store、共享组件、API、依赖清单、锁文件或应用配置；换分支、暂不提交、先改后撤也仍是正式代码写入。

记录 Approval：用户授权原文或消息定位、方案版本、允许的行为范围、排除项、是否明确跳过原型、尚存限制。普通内部实现细节不变更产品行为和范围时，不反复求批准。

存在原型写入、范围变化、授权歧义、中断恢复或委派时，先读 [authorization-and-isolation.md](references/authorization-and-isolation.md)。

## 6. 在授权内实现

先核对最终 Requirement Brief、Impact Map、Prototype 和 Approval 是否一致；缺项只补必要内容，不重复完整流程。

获得有效授权且无阻塞后实际推进实现，不能靠持续等待避免风险。逐项修改已授权行为，保留无关功能与用户既有改动。

使用项目已有测试与实现习惯。已安装且适用时，复用调试、TDD、代码审查等流程，不在这里复制另一套。需要安装、联网、迁移、提交、推送或部署时，按环境权限分别处理，不能从“直接改”推导全部操作权限。

子 Agent 继承同一范围和 Gate。主 Agent 复核其文件增量与验证证据，不能以子 Agent 自报成功代替验收。

## 7. 验证行为后报告

验证前读取 [verification.md](references/verification.md)。围绕验收条件选择静态检查、行为测试、目标平台验证与范围外回归；不能只凭 Build／Lint 宣称完成。

筛选或表单变更按相关性检查：选择 → UI 状态 → Store／请求参数 → Reset → 重新打开与回显；还应覆盖默认值、互斥／从属关系和保存行为。

完成后按业务语义反向扫描相关入口，区分“已同步”“按范围保留”“尚未验证”；检查共享依赖有没有改变范围外行为，并与批准的 Prototype 对照。

所有通过声明绑定最终代码状态与实际证据。修改发生在验证之后时，重跑受影响检查；没有执行、环境受阻和执行失败分开报告，不把未知写成通过。

最终按四项交付：**改了什么；哪些范围保持不变；执行了什么验证及结果；仍未验证／待决事项。** 分开表述实现状态与验收状态，避免无依据的“全部完成”。
